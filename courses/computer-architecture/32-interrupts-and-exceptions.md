# Chapter 32: Interrupts and Exceptions

The CPU executes instructions one after another, but the world outside the CPU doesn't operate on the CPU's schedule. A keyboard key is pressed. A network packet arrives. A timer fires. A program divides by zero. Without a mechanism to handle these asynchronous events, the CPU would have to waste cycles constantly checking whether anything had happened — or worse, ignore these events entirely. **Interrupts and exceptions** are the mechanism by which the CPU stops what it's doing, handles an external event or error, and resumes the original work — all while preserving the illusion that execution was never interrupted.

## 1. The Problem: Asynchronous Events

Without interrupts, a program that wants to read keyboard input must **poll** — repeatedly check if a key was pressed:

```
while (true) {
    if (keyboard_register_ready) {
        char = keyboard_register_data;
        process(char);
    }
    do_other_work();
}
```

Polling has several problems:
1. **CPU time wasted** checking devices that rarely have data
2. **Latency**: you only notice the keypress on the next poll iteration — could be millions of cycles later
3. **Blocking**: if `do_other_work()` takes too long, you miss events

**Interrupts** invert this model: instead of the CPU asking "do you have data?", the device tells the CPU "I have data!" — and the CPU responds only when needed.

The same problem exists for internal events: what should happen when a program tries to divide by zero? Access an unmapped memory address? Execute an illegal instruction? The CPU needs a standard mechanism to detect these and transfer control to the OS.

## 2. Interrupts — External Signals

A **hardware interrupt** (also called an **IRQ**, Interrupt Request) is an electrical signal sent from a hardware device to the CPU indicating that it needs attention.

Sources of hardware interrupts:
- **Keyboard**: key pressed or released
- **Timer**: programmable interval timer fires (used by the OS scheduler every ~1ms)
- **Network card**: packet received
- **Disk controller**: I/O transfer complete
- **GPU**: frame rendering complete
- **USB controller**: device connected/disconnected

### Interrupt Lines and the APIC

Historically, devices connected to the CPU via dedicated **IRQ lines** (Intel 8259 PIC had 16 IRQ lines). Modern systems use the **APIC (Advanced Programmable Interrupt Controller)**:

- **Local APIC** (LAPIC): integrated into each CPU core. Manages interrupts for that specific core — timer, inter-processor interrupts (IPIs), thermal alerts.
- **I/O APIC**: on the motherboard. Routes external interrupts (keyboard, PCIe devices) to the appropriate CPU core.

**MSI (Message Signaled Interrupts)**: Instead of dedicated interrupt lines, PCIe devices write a small message to a special memory address. The APIC interprets this message as an interrupt. MSI allows many more interrupt vectors and avoids the "IRQ sharing" problems of legacy PIC.

```
Modern interrupt routing:
  PCIe device → MSI write to memory address → I/O APIC → LAPIC → CPU core
  Timer → LAPIC directly → CPU core
  IPI → LAPIC of other cores → target cores
```

**NMI (Non-Maskable Interrupt)**: Most interrupts can be temporarily disabled by the CPU (masked) to handle critical sections. NMI cannot be masked — it always interrupts. Used for hardware failures (memory errors, machine checks), hardware debuggers (JTAG), and watchdog timers.

## 3. Exceptions — Internal CPU Events

**Exceptions** (also called faults, traps, or aborts depending on type) are generated by the CPU itself in response to an instruction or condition, not by external hardware.

### Classification by Recoverability

**Fault**: An exception that can be corrected and the instruction retried.
- Page fault: OS loads the page from disk, then retries the faulting instruction
- General Protection Fault: attempt to access a privileged resource — kills the process

**Trap**: A synchronous exception triggered intentionally. Execution continues at the instruction after the trap.
- Breakpoint (`INT 3` on x86): debugger places this to stop at a specific point
- System call (`SYSCALL` / `INT 0x80`): intentional transfer to kernel

**Abort**: A fatal, unrecoverable error.
- Double fault: another exception occurs while handling an exception
- Machine check exception (MCE): hardware detected an uncorrectable error (RAM ECC failure, CPU internal parity error)
- Results in system hang, crash dump, or reboot

### Common x86 Exception Numbers

| Vector | Name | Type | Cause |
|--------|------|------|-------|
| 0 | #DE Divide Error | Fault | Division by zero |
| 1 | #DB Debug | Fault/Trap | Breakpoint, watchpoint |
| 3 | #BP Breakpoint | Trap | INT 3 instruction |
| 6 | #UD Invalid Opcode | Fault | Unknown instruction |
| 8 | #DF Double Fault | Abort | Exception during exception |
| 13 | #GP General Protection | Fault | Privilege violation |
| 14 | #PF Page Fault | Fault | Missing/invalid page |
| 18 | #MC Machine Check | Abort | Hardware error |

## 4. The Interrupt Handling Sequence

When an interrupt or exception occurs, the CPU performs the following sequence — entirely in hardware (microcode level):

**1. Finish (or abandon) the current instruction**
- For exceptions (synchronous): the instruction that caused the exception is the last one executed before the handler
- For hardware interrupts (asynchronous): usually waits for the current instruction to complete

**2. Save machine state on the kernel stack**
The CPU pushes the following registers onto the kernel stack (x86-64):
```
Stack grows downward:
  [SS]              (Stack Segment, if privilege change)
  [RSP]             (user stack pointer, if privilege change)
  [RFLAGS]          (flags register — condition codes, interrupt enable flag)
  [CS]              (Code Segment)
  [RIP]             (Instruction Pointer — where to return to)
  [Error Code]      (some exceptions only, e.g., page fault)
```

**3. Switch to kernel mode**
The CPU changes the privilege level from ring 3 (user) to ring 0 (kernel) and loads the kernel stack pointer.

**4. Look up the handler address in the IDT**
The interrupt vector number indexes into the **Interrupt Descriptor Table (IDT)** to find the handler function address.

**5. Jump to handler**
The CPU jumps to the handler address. The OS kernel's handler code runs.

**6. Handler executes**
- Save additional registers (the rest of the register file) — the CPU only saved the minimum automatically
- Identify the cause (examine error codes, query device registers)
- Handle it (service the device, fix the condition, kill the process, etc.)
- Restore additional registers

**7. Return from interrupt (IRET / ERET)**
The `IRET` instruction (x86) atomically:
- Pops RIP, CS, RFLAGS, RSP, SS from the kernel stack
- Switches back to user mode
- Resumes execution at the saved RIP

```
Timeline:
  User code: instruction N, instruction N+1...
  [interrupt asserted]
  → Hardware saves state, jumps to kernel handler
  → Kernel handles interrupt (services device, etc.)
  → IRET
  → User code resumes at instruction N+2 (no visible effect)
```

The user process has no idea the interrupt happened. This is the magic of transparent interrupt handling.

## 5. Privilege Levels — Ring 0 and Ring 3

Modern CPUs enforce **privilege levels** — different levels of trust for code that can be executed.

**x86 privilege levels (rings)**:
- **Ring 0 (kernel mode)**: full access to all hardware, all instructions, all memory. OS kernel code runs here.
- **Ring 1, Ring 2**: historically for OS subsystems, now rarely used (Linux/Windows use only rings 0 and 3).
- **Ring 3 (user mode)**: restricted access. Cannot access kernel memory, cannot execute privileged instructions (`HLT`, `CLI`, `IN`/`OUT`, `WRMSR`, etc.).

```
Protection:
  Ring 3 code: can only access its own memory (virtual addresses in user space)
               cannot use privileged instructions
               cannot access I/O ports directly
               → any attempt causes #GP (General Protection Fault)
  
  Ring 0 code: full access to everything
               runs with interrupts disabled if needed
               can modify page tables, write to hardware registers
```

**Why this matters**: If a program could execute `CLI` (clear interrupt flag — disable all interrupts), it could freeze the system. If it could write to memory-mapped I/O registers, it could reprogram hardware. If it could modify page tables, it could access other processes' memory. Ring isolation prevents all of this.

**Hypervisor (Ring -1)**: With hardware virtualization (Intel VT-x, AMD-V), there's a new privilege level below ring 0 — the **VMX root mode** or **hypervisor mode**. The hypervisor (e.g., KVM, Hyper-V) runs here, while guest OS kernels think they're in ring 0 but are actually in a restricted "guest ring 0" (VMX non-root). Guest OS page tables and privileged instructions are intercepted by the hypervisor.

## 6. System Calls — The User-Kernel Interface

User programs often need services that require kernel privileges: reading files, opening network connections, allocating memory. They can't do this directly (ring 3 can't access kernel resources). Instead, they make **system calls** — a controlled, safe transition from ring 3 to ring 0.

**x86-64 `SYSCALL` instruction**:
1. User program loads syscall number into RAX (e.g., 0 = read, 1 = write, 2 = open)
2. Load arguments into RDI, RSI, RDX, R10, R8, R9
3. Execute `SYSCALL` instruction
4. CPU saves RIP and RFLAGS, switches to ring 0, loads the kernel entry point address from the `LSTAR` MSR
5. Kernel handler: checks RAX to determine which syscall, validates arguments, performs the operation
6. Kernel executes `SYSRET` to return to ring 3

```
Linux read() syscall path:
  User: read(fd, buf, count)
  ↓  C library wrapper: mov rax, 0; mov rdi, fd; mov rsi, buf; mov rdx, count; syscall
  ↓  CPU: save rip, switch to ring 0, jump to linux_kernel_entry_SYSCALL_64
  ↓  Kernel: validate fd; check permissions; copy data from kernel buffer to user buf
  ↓  Kernel: sysret
  ↓  User: read() returns with bytes read in rax
```

**Performance**: A system call has significant overhead — typically 100–1000 ns. Switching between ring 3 and ring 0 requires:
- TLB/cache effects (switching page tables, particularly after Meltdown/KPTI mitigations)
- Saving/restoring registers
- Kernel entry path security checks

This is why batching small I/O operations (avoid calling `write()` 1 byte at a time) and using techniques like `io_uring` (Linux 5.1+, allows user programs to submit many I/O requests without individual syscalls) are important for performance.

**vDSO (Virtual Dynamic Shared Object)**: The Linux kernel maps a small section of kernel code into every process's address space. This allows certain "syscalls" (like `gettimeofday()`) to be executed without actually entering the kernel — just a function call within the process. The gettimeofday VSDO reads a kernel-maintained time variable directly from its mapped region. Essentially free (no privilege switch).

## 7. The Interrupt Descriptor Table

The **IDT (Interrupt Descriptor Table)** is the x86 data structure that maps interrupt/exception vector numbers to handler function addresses. It is set up by the OS kernel at boot time and protected (only kernel can modify it).

```
IDT structure:
  Vector 0:  Divide Error handler → address of #DE handler function
  Vector 1:  Debug handler        → address of #DB handler function
  ...
  Vector 14: Page Fault handler   → address of #PF handler function
  ...
  Vector 32-255: Hardware interrupts (configurable)
  
  Each entry (gate descriptor): 16 bytes
    - Handler address (split across entry)
    - Privilege level (DPL): ring 0 only, or ring 3 allowed
    - Gate type: interrupt gate (disables further interrupts) vs trap gate (leaves enabled)
```

**Interrupt gate vs Trap gate**: An interrupt gate handler runs with interrupts disabled (the CPU clears the IF flag in RFLAGS). This prevents a new interrupt from interrupting the handler — important for atomicity. A trap gate handler runs with interrupts enabled (useful for system calls that may need to be interrupted if they run long).

**LIDT instruction**: Loads the IDT register (IDTR) with the base address and size of the IDT table. Ring 0 only. If the IDTR is corrupted (by a bug or attack), the system can't handle any exceptions — instant kernel panic.

**ARM equivalent**: ARM uses the **Exception Vector Table** at a fixed address (e.g., 0xFFFF0000 in ARM32, or VBAR_EL1 register in AArch64). Each entry is a branch instruction to the actual handler. The concept is the same as x86 IDT.

## Summary

- **Polling** wastes CPU cycles and has high latency. **Interrupts** allow hardware to notify the CPU asynchronously and efficiently.
- **Hardware interrupts** (IRQs) come from external devices (timer, keyboard, NIC) via the APIC. **Exceptions** are generated by the CPU itself (page fault, divide by zero, breakpoint).
- The **interrupt handling sequence**: save state, switch to ring 0, look up IDT, execute handler, `IRET` back to user code — completely transparent to the user process.
- **Privilege levels** (ring 0 / ring 3) enforce CPU-level isolation. User code can't execute privileged instructions or access kernel memory.
- **System calls** (`SYSCALL` instruction) provide a controlled ring 3 → ring 0 transition for OS services. Each call has overhead (~100–1000 ns); minimizing call count matters.
- The **IDT** maps vector numbers to handler addresses. Set up by the kernel at boot.
