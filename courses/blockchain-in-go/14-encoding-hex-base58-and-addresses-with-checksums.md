# Chapter 14: Encoding — Hex, Base58, and Addresses with Checksums

Chapter 13 left you holding a working `KeyPair`, and inside it, a `PublicKey`: 64 raw bytes anyone can use to verify Alice's signatures. Sixty-four raw bytes is exactly the right shape for a computer to work with, and exactly the wrong shape for a human being. Nobody wants to read a public key aloud over the phone, copy it by hand into a chat message, or type it correctly on the first try — and in a system where a single mistyped character could send money to the wrong person forever, "close enough" is not good enough. This chapter builds the encoding GoChain uses to turn a public key into something a human can actually read, write down, and — crucially — get *right*, or find out immediately if they got it wrong: a Base58-encoded address with a built-in checksum.

## 1. What We Have So Far: A 64-Byte Public Key

Chapter 13, Section 5 fixed GoChain's public key format: the elliptic curve point's `X` and `Y` coordinates, each padded to 32 bytes for P-256, concatenated with no other framing — 64 raw bytes total. Printed as hexadecimal (Chapter 09, Section 3), one real public key generated by `crypto.NewKeyPair()` looks like this:

```
93c4523e142bcae1d6dce6e9d3beb4197dc6dcb03507ebd6b4d1470316a340c
6382d8a88fcd3ff008c90c43e9cd080ec2755ae5fc71d5601ad13394d6ec6457c
```

(split across two lines here purely for readability — it is one continuous 128-character string). This is completely correct, completely unambiguous, and completely unusable as something a person types into a wallet app to send GoChain funds to a friend. This chapter's entire job is closing that gap.

---

## 2. The Problem With Raw Public Keys

It is worth being specific about exactly what makes a 128-character hex string hostile to humans, because each specific problem points toward a specific fix later in this chapter:

- **It is long.** 128 characters is far more than anyone reliably copies correctly by hand, especially across a phone call, a photograph of a screen, or a hastily typed chat message.
- **It offers no way to catch a mistake.** If you mistype one hex character while transcribing an address, nothing about the string itself tells you anything went wrong. The transaction would simply go to a *different*, entirely valid-looking public key — possibly one nobody controls, or worse, one somebody else does — and there would be no error, no warning, and (as Chapter 11, Section 10 already established for a lost private key) no way to undo it once it is mined into a block.
- **It exposes the raw cryptographic material directly.** There is no strict security requirement to hide a public key (Chapter 11, Section 2 was explicit that public keys are meant to be shared freely), but a shorter, purpose-built format still has room to add useful structure — like a version byte (Section 11) — that a raw key alone does not carry.

The first problem (length) and the third (structure) are solvable with any reasonable encoding. The second problem — catching mistakes — needs a specific, deliberate design choice, and it is the one most existing generic encodings do not solve at all. Sections 3 and 4 look at two encodings you likely already know, precisely to see why neither one is what GoChain reaches for.

## 3. Hex, Revisited — and Where It Falls Short

Chapter 09 already introduced hexadecimal encoding, and it remains exactly the right tool for the jobs this course has used it for so far: printing a hash to a terminal, logging a value for debugging, storing a fingerprint as readable text in this book's own diagrams. Hex is simple, unambiguous, and every programmer recognizes it on sight.

But hex is a poor fit for something a person needs to *transcribe correctly by hand*, for one very concrete reason: it uses only 16 symbols (`0-9` and `a-f`) to represent 8 bits per byte, which means a 64-byte public key becomes 128 hex characters — the entire length problem from Section 2, undiminished. Hex encoding is *dense in symbols used* but *sparse in information per character*, exactly the wrong trade for something meant to be short and readable. A better encoding would pack more information into each character, using a larger alphabet, so the same underlying bytes produce a noticeably shorter string.

---

## 4. Base64 — Closer, But Not Quite Right

**Base64** is a common answer to "use a larger alphabet to shorten the string": it uses 64 symbols (`A-Z`, `a-z`, `0-9`, plus two extra characters, conventionally `+` and `/`) instead of hex's 16, packing 6 bits of information into every character instead of 4. The same 64-byte public key that took 128 hex characters takes roughly 88 Base64 characters — a real, meaningful improvement in length.

Base64 solves Section 2's length problem reasonably well. It does nothing at all for the mistake-catching problem, and it actively makes one thing worse: Base64's alphabet includes characters that are easy to visually confuse with each other, or that behave inconveniently once a human is involved in copying them by hand:

```
  Confusable in many fonts, when handwritten, or read aloud:

  0  (zero)         vs.  O  (capital letter O)
  1  (one)          vs.  l  (lowercase L)   vs.  I  (capital letter i)

  Base64's alphabet includes ALL of these characters. A person
  transcribing a Base64 string has no help telling them apart.
```

Base64 also includes `+` and `/`, which cause their own headaches in contexts like URLs and filenames (where those characters have special meaning), and it typically adds `=` padding characters at the end to make the encoded length a multiple of four — one more detail a human copying the string by hand has to get exactly right. None of this makes Base64 a bad encoding; it does its actual job (compact, reversible, byte-safe text) very well. It simply was never designed with "a person will read this over the phone or handwrite it onto a piece of paper" as a goal, and Bitcoin's original designers wanted exactly that goal solved directly.

---

## 5. Base58 — Removing Ambiguous Characters

**Base58** is Base64's more human-friendly cousin, and it is the encoding Bitcoin introduced for exactly this purpose — GoChain uses the same one. It starts from a 58-character alphabet and deliberately removes every character Section 4 flagged as visually confusable, plus the two symbol characters that caused practical headaches:

```
  Base58 alphabet (58 characters):

  123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz

  Removed, on purpose, compared to a full alphanumeric set:

  0  (zero)              -- confusable with capital O
  O  (capital letter O)  -- confusable with zero
  I  (capital letter i)  -- confusable with lowercase l
  l  (lowercase L)       -- confusable with capital I
  +  and  /              -- Base64's symbol characters, dropped entirely
```

Every remaining character in Base58's alphabet is a letter or digit, and no two of them look alike even in a low-resolution photo, a handwritten note, or a font that renders `0` and `O` nearly identically. This is a small design choice with an outsized practical payoff: it does not prevent every possible transcription error, but it eliminates an entire, extremely common *category* of error — the "I copied this correctly, but that squiggle was a one, not a lowercase L" mistake — for free, just by choosing the alphabet carefully. GoChain addresses (Section 11) and, later, wallet seed-phrase-derived keys (Volume 6) both benefit from this same careful alphabet choice.

## 6. Implementing Base58Encode

Base58 encoding works the same way any positional-base conversion does — the same idea as converting a number from decimal to binary, just with a base of 58 instead of 2 or 10. Treat the entire input byte slice as one enormous number, then repeatedly divide it by 58, using each remainder to pick a character from the alphabet, until nothing is left:

```go
// crypto/base58.go
package crypto

import "math/big"

// b58Alphabet is Bitcoin's Base58 alphabet: every digit and letter
// except 0, O, I, and l (Section 5), plus no symbol characters at all.
var b58Alphabet = []byte("123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz")

// Base58Encode converts input into GoChain's Base58 text encoding.
func Base58Encode(input []byte) []byte {
	var result []byte

	x := new(big.Int).SetBytes(input)

	base := big.NewInt(58)
	zero := big.NewInt(0)
	mod := &big.Int{}

	for x.Cmp(zero) != 0 {
		x.DivMod(x, base, mod)
		result = append(result, b58Alphabet[mod.Int64()])
	}

	// A leading 0x00 byte carries real information (it is not the
	// same as "no bytes at all"), but big.Int treats leading zero
	// bytes as insignificant and silently drops them. Bitcoin's fix,
	// which GoChain follows: represent each leading 0x00 input byte
	// as a leading '1' character (b58Alphabet[0]) in the output.
	for _, b := range input {
		if b != 0x00 {
			break
		}
		result = append(result, b58Alphabet[0])
	}

	reverseBytes(result)
	return result
}

func reverseBytes(b []byte) {
	for i, j := 0, len(b)-1; i < j; i, j = i+1, j-1 {
		b[i], b[j] = b[j], b[i]
	}
}
```

Two Go details worth pausing on. First, `big.Int` is Go's arbitrary-precision integer type (Chapter 09 never needed it, since SHA-256 digests are handled as plain byte slices, but a 64-byte number is far too large for any built-in numeric type like `int64`) — exactly the right tool for treating a whole byte slice as one giant number. Second, the digits come out of the `for` loop in least-significant-first order (the same way you would compute decimal digits one at a time by repeatedly dividing by 10, getting the ones digit first), so `reverseBytes` flips the result before returning it — forgetting this step is an easy, silent bug: the code would still run, but every encoded address would come out backwards.

The leading-zero handling deserves one more sentence, because it is easy to gloss over: a GoChain address (Section 11) always starts with a version byte, and GoChain's version byte is `0x00` — meaning *every single address this chapter produces* depends on this exact leading-zero-byte handling to encode correctly at all. Skipping it would not just be a cosmetic bug; it would silently drop the version byte from every address's leading edge.

## 7. Implementing Base58Decode

Decoding reverses the process: read the encoded characters left to right, treating each one as a digit in base 58, building the number back up by repeated multiplication and addition — and then re-inserting however many leading zero bytes Section 6's encoding step removed from the numeric representation:

```go
import "bytes"

// Base58Decode reverses Base58Encode, recovering the original bytes.
func Base58Decode(input []byte) []byte {
	result := big.NewInt(0)
	base := big.NewInt(58)

	for _, b := range input {
		charIndex := bytes.IndexByte(b58Alphabet, b)
		result.Mul(result, base)
		result.Add(result, big.NewInt(int64(charIndex)))
	}

	decoded := result.Bytes()

	// Restore however many leading 0x00 bytes Base58Encode represented
	// as leading '1' characters (Section 6).
	numLeadingOnes := 0
	for _, b := range input {
		if b != b58Alphabet[0] {
			break
		}
		numLeadingOnes++
	}

	return append(bytes.Repeat([]byte{0x00}, numLeadingOnes), decoded...)
}
```

This chapter's version of `Base58Decode` deliberately keeps its contract simple, matching the plain `func Base58Decode(input []byte) []byte` signature: it assumes `input` is well-formed Base58 text, produced by `Base58Encode` (or an equally well-formed address someone typed correctly). `bytes.IndexByte` returns `-1` for any character not in `b58Alphabet` at all — a production-grade version of this function would check for that and return an explicit error rather than silently corrupting `result` with a `-1` index, and Exercise 6 asks you to add exactly that guard yourself. For this chapter's purposes, the real safety net against a *mistyped* character living inside otherwise-valid Base58 text is not `Base58Decode` at all — it is the checksum built in Sections 9 and 10.

Try both functions together and confirm they round-trip correctly:

```go
original := []byte{0x00, 0x01, 0x02, 0x03}
encoded := crypto.Base58Encode(original)
decoded := crypto.Base58Decode(encoded)
fmt.Println(bytes.Equal(original, decoded)) // true
```

## 8. Why Typos Are a Real, Costly Threat

Section 5's careful alphabet choice prevents one category of transcription error — visual confusion between similar-looking characters. It does nothing at all to catch the far more common case: a person simply fat-fingering a character while typing, whether or not that character happens to look like another one. Swap one letter for an adjacent key on the keyboard, drop one character entirely, transpose two characters — any of these produces a *different but still perfectly valid-looking* Base58 string, decodable by `Base58Decode` into some other 64-byte public key (or, more precisely, into the pieces of some other address entirely — Section 11 covers the full shape).

This is not a hypothetical risk invented for this course, in the same spirit as Chapter 11, Section 4's real-world private key theft stories. Sending cryptocurrency to a mistyped address is one of the most common, and most permanently costly, mistakes in the entire history of Bitcoin and Ethereum: there is no bank to call, no "undo send" button, and (exactly as Chapter 11, Section 10 explained for a lost private key) no central authority capable of reversing a transaction once it is confirmed. If a mistyped address happens to decode into *some* validly-shaped destination — which, for a long enough random-looking string, is common — the funds are simply gone, sent to wherever that typo pointed, forever.

```
  Alice means to send funds to:
  1BvBMSEYstWetqTFn5Au4m4GFg7xJaNVN2

  Alice actually types (one character changed):
  1BvBMSEYstWetqTFn5Au4m4GFg7xJaNVK2
                                  ^
                             one typo

  Both strings are the same length, both LOOK like plausible
  addresses. Without a checksum, nothing distinguishes "a genuine
  address" from "a typo that happens to still be valid Base58 text."
```

## 9. Checksums — Catching Typos Before They Cost You

A **checksum** is a small, extra piece of data, derived from the rest of a message by some deterministic function, whose entire job is to answer one question fast: "does this data still match what it was supposed to be?" You have almost certainly relied on a checksum before without necessarily using the word — the last digit of a credit card number (a checksum called the Luhn algorithm) exists specifically so that a single mistyped digit gets caught by the card processor before the transaction is even attempted, rather than being silently charged to a different, real card number.

GoChain's checksum works on exactly the same principle, applied to an address instead of a credit card. Before encoding an address, GoChain computes a short hash-derived checksum from the address's other bytes and appends it to the payload before Base58-encoding the whole thing. On the way back in — whenever GoChain needs to validate an address someone typed or pasted in — it recomputes that same checksum from the decoded payload and compares it against the checksum bytes that were appended:

```
   Building an address:                 Validating an address:

   payload bytes                        decoded bytes (payload + checksum)
        │                                        │
        ▼                                        ▼
   compute checksum                     split into payload + checksum
        │                                        │
        ▼                                        ▼
   append checksum                      recompute checksum from payload
   to payload                                     │
        │                                        ▼
        ▼                              compare recomputed checksum
   Base58-encode                        against the checksum that was
   the combined bytes                   actually appended

                                         match?    -> address is intact
                                         mismatch? -> reject immediately,
                                                      before ever sending
                                                      a single gochip
```

A single mistyped character almost never happens to *also* produce a checksum that still matches — this is exactly the avalanche effect (Chapter 08, Section 3) working in the checksum's favor: change one bit of the payload, and the hash used to compute the checksum changes completely and unpredictably, so a mismatched checksum is overwhelmingly the expected outcome of any accidental change, not a rare coincidence.

## 10. Implementing PubKeyHash and Checksum

Before the checksum, GoChain needs a shorter stand-in for the full 64-byte public key. Real Bitcoin addresses use SHA-256 followed by a second hash function, RIPEMD-160, to shrink a public key down to a fixed 20 bytes; RIPEMD-160 is not part of Go's standard library, and, following exactly the same reasoning Chapter 12, Section 3 used to justify P-256 over secp256k1, this course avoids pulling in a third-party package for something a standard-library-only substitute can achieve just as well for a learning project. GoChain instead takes the first 20 bytes of a SHA-256 hash — the same fixed 20-byte length Bitcoin's approach produces, using only the `crypto.Hash` function this course already has:

```go
// PubKeyHash returns a fixed 20-byte fingerprint of pubKey, suitable
// for embedding in a short, human-facing address. Real Bitcoin
// chains this with RIPEMD-160 after SHA-256; GoChain instead
// truncates a SHA-256 digest to the same 20-byte length, avoiding a
// dependency outside Go's standard library while keeping addresses
// exactly as short.
func PubKeyHash(pubKey []byte) []byte {
	fullHash := Hash(pubKey) // crypto.Hash, Chapter 09 -- 32 bytes
	return fullHash[:20]
}
```

`Checksum` follows Bitcoin's exact recipe: hash the payload with SHA-256 twice in a row (a **double hash**, a Bitcoin convention adopted here directly, since Go's standard-library SHA-256 is exactly the hash this course already trusts), and keep only the first 4 bytes of that second hash:

```go
// checksumLength is the number of checksum bytes appended to an
// address's payload before Base58-encoding it.
const checksumLength = 4

// Checksum computes a short, typo-detecting fingerprint of payload:
// SHA-256, applied twice, truncated to the first 4 bytes.
func Checksum(payload []byte) []byte {
	firstHash := Hash(payload)
	secondHash := Hash(firstHash)
	return secondHash[:checksumLength]
}
```

Four bytes is a deliberate, practical trade-off, not an arbitrary choice: it is short enough to keep the final address compact, while still making an *accidental* checksum match astronomically unlikely for a random typo — a 4-byte checksum has roughly 1-in-4-billion odds of matching by pure chance, which is more than enough to catch the ordinary, unintentional mistakes this feature exists to catch. It offers no protection at all against a deliberate, malicious forgery (Volume 5's transaction validation, not this chapter's checksum, is what protects against a bad actor deliberately trying to steal funds) — the checksum's entire job, precisely and only, is catching honest transcription mistakes before they become permanent.

## 11. Assembling a GoChain Address

With `PubKeyHash`, `Checksum`, and `Base58Encode` all in hand, a GoChain address is simply these three pieces, concatenated in a fixed order:

```
  ┌──────────┬────────────────────┬───────────┐
  │  version │    PubKeyHash       │ checksum  │
  │ (1 byte) │    (20 bytes)       │ (4 bytes) │
  └──────────┴────────────────────┴───────────┘
                       │
                       ▼
              Base58Encode(...)
                       │
                       ▼
           a short, typo-resistant,
           human-readable GoChain address
```

The **version byte** is a single byte prepended before the public key hash, and GoChain uses `0x00` for it throughout this course. Its job is to identify what *kind* of address this is — real Bitcoin uses different version bytes to distinguish a normal address from other special address types, and a future GoChain chapter could do the same (for example, to distinguish a real address from a test-network address) without changing anything else about how an address is built or decoded. Including it from the very first chapter that builds addresses, even though GoChain only ever uses one version value today, means nothing about the address *format* needs to change later if that need arises — exactly the kind of forward-looking design choice worth making once, early, rather than retrofitting later.

```go
// version is GoChain's single address version byte. Every address
// this course produces starts with this exact byte.
const version = byte(0x00)
```

Notice that `Checksum` (Section 10) is computed over the version byte *and* the public key hash together, not the public key hash alone — this means the checksum also catches a corrupted version byte, not just a corrupted hash, closing a gap a less careful design might leave open.

## 12. Full Worked Example: From Public Key to Address, and Catching a Typo

Here is the complete pipeline, end to end, starting from a real key pair generated by Chapter 13's `NewKeyPair()`:

```go
package main

import (
	"encoding/hex"
	"fmt"

	"github.com/you/gochain/crypto"
)

const version = byte(0x00)

func main() {
	kp, _ := crypto.NewKeyPair()

	pubKeyHash := crypto.PubKeyHash(kp.PublicKey)
	versionedPayload := append([]byte{version}, pubKeyHash...)
	checksum := crypto.Checksum(versionedPayload)
	fullPayload := append(versionedPayload, checksum...)

	address := crypto.Base58Encode(fullPayload)
	fmt.Println("address:", string(address))
}
```

One real run of this exact code produced the following (your own run will differ, since `NewKeyPair` draws a fresh random private key every time — Chapter 11, Section 2):

```
public key:        93c4523e142bcae1d6dce6e9d3beb4197dc6dcb03507ebd6b4d1470316a340c
                    6382d8a88fcd3ff008c90c43e9cd080ec2755ae5fc71d5601ad13394d6ec6457c
pubKeyHash:         6b0ce9666b72c79381e11cb6989406d8aed3e662
versionedPayload:   006b0ce9666b72c79381e11cb6989406d8aed3e662
checksum:           fe6fda54
fullPayload:        006b0ce9666b72c79381e11cb6989406d8aed3e662fe6fda54
address:            1Am2meaGsuppgds5MN7tJDkr2PMmMFfYfD
```

Notice the address starts with `1` — that leading `1` is exactly Section 6's leading-zero-byte handling in action, produced directly by the `0x00` version byte at the very front of `fullPayload`. Every GoChain address in this course will start with `1` for that same reason, the same way every real Bitcoin mainnet address happens to start with `1` for an analogous reason.

Now, the payoff this entire chapter has been building toward — simulate exactly the kind of typo Section 8 described, changing a single character of the address, and watch validation catch it before anything gets sent anywhere:

```go
	typo := []byte(string(address))
	typo[1] = 'B' // change one character -- a plausible, easy typo

	decoded := crypto.Base58Decode(typo)
	gotVersion := decoded[0]
	gotHash := decoded[1 : len(decoded)-4]
	gotChecksum := decoded[len(decoded)-4:]

	expectedChecksum := crypto.Checksum(append([]byte{gotVersion}, gotHash...))
	valid := hex.EncodeToString(gotChecksum) == hex.EncodeToString(expectedChecksum)

	fmt.Println("typo'd address:", string(typo))
	fmt.Println("checksum valid:", valid)
```

This prints:

```
typo'd address:  1Bm2meaGsuppgds5MN7tJDkr2PMmMFfYfD
checksum valid:  false
```

One changed character, and the checksum comparison immediately flags the address as corrupted — exactly the "reject before ever sending a single gochip" outcome Section 9's diagram promised, and exactly the failure mode Section 8 warned costs real money, permanently, when it goes uncaught. A real GoChain wallet (Volume 6) would perform this exact check the instant a user pastes or types an address, refusing to build a transaction at all until the checksum matches.

## 13. Where This Fits in GoChain

`PubKeyHash`, `Checksum`, `Base58Encode`, and `Base58Decode` are the exact four primitives Volume 6's `wallet.Address()` (Chapter 40) wraps into a single, convenient method, and the exact same primitives Volume 5's transaction-building code (Chapter 32) uses whenever it needs to turn a recipient's typed-in address back into the raw public key hash a transaction actually spends to. The version byte introduced in Section 11 as "currently always `0x00`" becomes genuinely useful starting in Chapter 40, once GoChain needs to tell a real address apart from a test-network one. Nothing about the encoding itself changes from here forward — every later chapter that touches an address is either producing one with these exact functions, or validating one a user typed in with this exact checksum check.

## Summary

- A raw 64-byte public key (Chapter 13) is too long, too easy to mistype, and offers no way to catch a transcription error — this chapter builds an encoding that fixes all three problems at once.
- **Hex** is unambiguous but dense in characters used per byte, making it too long for something a human needs to transcribe by hand; **Base64** shortens the string but includes visually confusable characters (`0`/`O`, `1`/`l`/`I`) and symbol characters that cause practical headaches.
- **Base58** removes exactly those confusable and awkward characters from its alphabet, at the cost of slightly less information packed per character than Base64 — a deliberate trade favoring human transcription over maximum compactness.
- `Base58Encode` and `Base58Decode` treat a byte slice as one giant number and convert it to and from base 58, with special handling for leading `0x00` bytes (encoded as leading `'1'` characters) so no information is silently lost.
- A **checksum** is a small, derived value appended to data specifically so that any accidental change can be caught by recomputing and comparing it — GoChain's `Checksum` is a double SHA-256 hash of the payload, truncated to 4 bytes.
- `PubKeyHash` shrinks a 64-byte public key down to a fixed 20 bytes using `crypto.Hash`, standing in for Bitcoin's SHA-256-then-RIPEMD-160 approach without requiring a package outside Go's standard library.
- A GoChain address is `version || PubKeyHash || Checksum(version || PubKeyHash)`, Base58-encoded — the version byte identifies the address type, and the checksum, computed over both the version byte and the hash together, catches a corrupted address before a single transaction is ever built against it.
- The worked example proved this concretely: changing one character of a real, generated address caused the recomputed checksum to mismatch immediately, exactly the "catch it before it costs you" guarantee this entire chapter was built around.
