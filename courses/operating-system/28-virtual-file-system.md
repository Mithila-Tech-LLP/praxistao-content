# Chapter 28: Virtual File System — VFS

> **"The VFS layer is one of the most elegant abstractions in operating systems. By defining a uniform interface — open, read, write, close, stat — it makes every storage device, network share, and kernel data structure look like a file. You write code for 'a file', and the VFS dispatches to ext4 or NFS or /proc automatically. Write once, work everywhere."**

## 1. The Problem VFS Solves

Imagine writing a program that needs to read a file. What if:
- The file is on an ext4 disk
- The file is on an NTFS USB drive
- The "file" is actually `/proc/cpuinfo` (generated by the kernel on demand)
- The "file" is a network share (NFS, SMB)
- The "file" is a pipe from another process

Without VFS:
```c
// Would need different code for every file system type!
if (filesystem == EXT4) {
    ext4_read(fd, buf, count);
} else if (filesystem == NTFS) {
    ntfs_read(fd, buf, count);
} else if (is_proc) {
    proc_read(fd, buf, count);
}
// This nightmare times every OS program that reads files
```

With VFS:
```c
// ONE interface works everywhere:
ssize_t bytes = read(fd, buf, count);
// VFS dispatches to the right implementation transparently
```

**VFS is an indirection layer** — an abstract interface that every file system and special filesystem implements. Applications talk to VFS; VFS talks to the real implementation.

## 2. The VFS Abstraction

VFS defines four abstract objects with operations:

```
┌──────────────────────────────────────────────────────────────────┐
│                  Application (user space)                        │
│    read() write() open() stat() readdir() link() chmod()         │
└──────────────────────────────────────────────────────────────────┘
                           │  system calls
┌──────────────────────────────────────────────────────────────────┐
│                  VFS Layer (kernel)                               │
│  Defines: superblock_ops, inode_ops, file_ops, dentry_ops        │
└──────────────────────────────────────────────────────────────────┘
         │                │               │              │
┌────────▼───┐   ┌────────▼───┐   ┌──────▼─────┐  ┌────▼──────┐
│   ext4     │   │   NTFS     │   │   /proc    │  │    NFS    │
│(real disk) │   │(real disk) │   │(generated) │  │(network)  │
└────────────┘   └────────────┘   └────────────┘  └───────────┘
```

**VFS is an object-oriented design in C:**
Each file system provides a set of function pointers that implement the abstract operations:
```c
struct file_operations {
    loff_t (*llseek)(struct file *, loff_t, int);
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*mmap)(struct file *, struct vm_area_struct *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    int (*fsync)(struct file *, loff_t, loff_t, int datasync);
    // ... many more
};
```

When you call `read(fd, buf, len)`, the kernel:
1. Looks up the file descriptor → finds the open file table entry → gets a `struct file *`
2. Calls `file->f_op->read(file, buf, len, &file->f_pos)`
3. This function pointer points to, e.g., `ext4_file_read_iter` or `proc_read` or `nfs_file_read`

## 3. VFS Objects in Linux

Linux VFS has four main objects:

**1. superblock (`struct super_block`)**
Represents a mounted file system. Contains:
```c
struct super_block {
    dev_t            s_dev;       // device identifier
    unsigned long    s_blocksize; // block size
    loff_t           s_maxbytes;  // max file size
    struct file_system_type *s_type;  // what type is this FS?
    const struct super_operations *s_op;  // operations (sync_fs, statfs, etc.)
    struct dentry    *s_root;     // root dentry of this FS
    // ...
};
```

**2. inode (`struct inode`)**
Represents a file/directory/symlink/etc. Generic version of what ext4/NTFS inode stores:
```c
struct inode {
    umode_t          i_mode;    // file type + permissions
    kuid_t           i_uid;     // owner
    kgid_t           i_gid;     // group
    loff_t           i_size;    // file size in bytes
    struct timespec64 i_atime;  // access time
    struct timespec64 i_mtime;  // modify time
    struct timespec64 i_ctime;  // change time
    unsigned int     i_nlink;   // hard link count
    dev_t            i_rdev;    // device (for device files)
    unsigned long    i_ino;     // inode number
    const struct inode_operations *i_op;  // create, lookup, link, unlink, symlink, mkdir...
    const struct file_operations  *i_fop; // read, write, open, close...
    struct address_space *i_mapping;  // page cache for this file
    // ...
};
```

**3. dentry (`struct dentry`)**
Represents a directory entry — a name → inode mapping. The **dentry cache** caches recent path lookups.
```c
struct dentry {
    struct inode    *d_inode;   // inode this dentry points to
    struct dentry   *d_parent;  // parent dentry
    struct qstr      d_name;    // the name component ("passwd", "etc", "home")
    struct list_head d_child;   // siblings in parent directory
    struct list_head d_subdirs; // children of this dentry (if directory)
    const struct dentry_operations *d_op;
    // ...
};
```

The dentry cache (dcache) avoids repeated disk lookups for the same path. Accessing `/usr/bin/ls` repeatedly: after first lookup, dentries for `usr`, `bin`, `ls` are cached in RAM.

**4. file (`struct file`)**
Represents an open file — the in-kernel state per open() call:
```c
struct file {
    struct path      f_path;     // dentry + vfsmount (which FS mount point)
    const struct file_operations *f_op;  // operations table
    spinlock_t       f_lock;
    loff_t           f_pos;      // current file offset
    unsigned int     f_flags;    // O_RDONLY, O_NONBLOCK, etc.
    fmode_t          f_mode;     // read/write permissions
    // ...
};
```

## 4. File System Registration

A file system driver registers itself with VFS:
```c
// ext4 registration (called when ext4 module is loaded):
static struct file_system_type ext4_fs_type = {
    .owner    = THIS_MODULE,
    .name     = "ext4",
    .mount    = ext4_mount,     // called on mount
    .kill_sb  = kill_block_super,
    .fs_flags = FS_REQUIRES_DEV, // needs a block device
};

static int __init ext4_init_fs(void) {
    return register_filesystem(&ext4_fs_type);
}

// Shows up in /proc/filesystems
```

**Viewing registered file systems:**
```bash
cat /proc/filesystems
# nodev  sysfs
# nodev  proc
# nodev  devtmpfs
# nodev  tmpfs
# nodev  devpts
#        ext3
#        ext4
#        vfat
#        ntfs
# nodev  nfs
# nodev  nfs4
# ...
```

The `nodev` prefix means the filesystem doesn't require a block device (proc, sysfs, tmpfs).

## 5. Mount Points — Composing the Namespace

**The Unix file system namespace** is a single unified tree. Multiple physical file systems are grafted onto this tree at **mount points**.

```
After boot:
/           (root ext4 on /dev/sda1)
├── usr/    (part of root ext4)
├── home/   (ext4 on /dev/sda2 — separate partition)
├── tmp/    (tmpfs — RAM-backed, no physical device)
├── proc/   (procfs — pseudo-filesystem)
├── sys/    (sysfs — pseudo-filesystem)
├── dev/    (devtmpfs — device files)
├── media/
│   └── usb0/  (vfat on /dev/sdb1 — USB drive, mounted here)
└── mnt/
    └── nfs/   (NFS mount — files are on another machine!)
```

**Mounting:**
```bash
# Mount ext4:
mount -t ext4 /dev/sdb1 /mnt/data

# Mount tmpfs (RAM disk):
mount -t tmpfs -o size=512m tmpfs /mnt/ramdisk

# Mount a loop device (disk image):
mount -o loop disk.img /mnt/image

# Bind mount (make /src appear at /dst):
mount --bind /source/dir /target/dir
# Now /target/dir shows exactly the same contents as /source/dir
# Useful for containers: bind mount the host's /etc into a container
```

**Viewing mounts:**
```bash
cat /proc/mounts
# or
findmnt
# TARGET        SOURCE      FSTYPE  OPTIONS
# /             /dev/sda1   ext4    rw,relatime
# /home         /dev/sda2   ext4    rw,relatime
# /proc         proc        proc    rw,nosuid,nodev,noexec
# /sys          sysfs       sysfs   rw,nosuid,nodev,noexec
# /dev          devtmpfs    devtmpfs rw
# /tmp          tmpfs       tmpfs   rw,nosuid,nodev
```

**Per-process namespaces (containers):**
Modern Linux can give each process its own **mount namespace** — its own independent view of the file system tree. This is how Docker containers work: each container sees only the files you want it to see.

## 6. /proc — The Process File System

`/proc` is a **pseudo-filesystem** — a fake file system with no disk backing. Reading a `/proc` file executes kernel code to generate the data on the fly.

**Per-process directories:**
```
/proc/1/         — init process (PID 1)
/proc/1234/      — process with PID 1234
  /proc/1234/cmdline   — command that launched this process (null-separated)
  /proc/1234/status    — process state, memory, permissions
  /proc/1234/maps      — memory-mapped regions (code, heap, stack, libraries)
  /proc/1234/fd/       — open file descriptors (each is a symlink to the file)
  /proc/1234/io        — I/O statistics (bytes read/written)
  /proc/1234/limits    — resource limits (ulimit values)
  /proc/1234/net/      — per-process network namespace info
  /proc/1234/mem       — can read/write process memory (ptrace uses this)
  /proc/1234/exe       — symlink to the executable
  /proc/1234/cwd       — symlink to current working directory
```

**System-wide files:**
```bash
cat /proc/cpuinfo       # CPU model, features, cores
cat /proc/meminfo       # RAM total/free/available/cached/swap
cat /proc/uptime        # seconds since boot
cat /proc/loadavg       # CPU load average (1m 5m 15m)
cat /proc/diskstats     # disk I/O statistics per device
cat /proc/net/tcp       # all TCP connections
cat /proc/interrupts    # interrupt count per IRQ per CPU
cat /proc/modules       # loaded kernel modules
cat /proc/filesystems   # registered file systems
cat /proc/mounts        # current mounts
ls /proc/sys/           # kernel sysctl parameters (read/write to tune kernel!)
```

**sysctl via /proc/sys:**
```bash
# Check if IP forwarding is enabled:
cat /proc/sys/net/ipv4/ip_forward
# 0

# Enable IP forwarding (makes this machine route packets):
echo 1 > /proc/sys/net/ipv4/ip_forward

# Disable ASLR (for debugging):
echo 0 > /proc/sys/kernel/randomize_va_space

# Adjust swappiness (how aggressively to swap to disk):
echo 10 > /proc/sys/vm/swappiness
```

## 7. /sys — The System File System

`/sys` (sysfs) exposes the kernel's **device model** as a file system hierarchy.

```
/sys/
├── block/           — block devices (sda, sdb, loop0)
│   └── sda/
│       ├── queue/   — I/O scheduler settings
│       │   ├── scheduler            # current scheduler (mq-deadline, kyber, none)
│       │   ├── read_ahead_kb       # readahead amount
│       │   └── rotational          # 1=HDD, 0=SSD
│       └── device/  — device info
├── bus/             — hardware buses (pci, usb, i2c, platform)
├── class/           — device classes (net, input, block, tty)
│   ├── net/
│   │   ├── eth0/    — network interface
│   │   │   ├── speed       (read: link speed in Mbps)
│   │   │   ├── operstate   (read: up/down)
│   │   │   └── address     (read: MAC address)
├── devices/         — complete device tree
├── kernel/          — kernel subsystem parameters
└── power/           — power management
```

**Tuning via /sys:**
```bash
# Switch I/O scheduler to none (no-op, good for NVMe SSDs):
echo none > /sys/block/nvme0n1/queue/scheduler

# Set readahead for HDD (2MB for sequential workloads):
echo 2048 > /sys/block/sda/queue/read_ahead_kb

# Disable USB power management for a device:
echo on > /sys/bus/usb/devices/1-1/power/control

# Trigger a hardware event (e.g., force fan speed check):
echo 1 > /sys/class/thermal/thermal_zone0/trip_point_0_temp
```

## 8. /dev — Devices as Files

Every device in Linux appears as a file in `/dev`:

**Major and minor numbers:**
```bash
ls -la /dev/sda* /dev/tty0 /dev/null
# brw-rw---- 1 root disk  8,  0 Jul 1 ... /dev/sda   (block, major 8, minor 0)
# brw-rw---- 1 root disk  8,  1 Jul 1 ... /dev/sda1  (block, major 8, minor 1)
# crw--w---- 1 root tty   4,  0 Jul 1 ... /dev/tty0  (char, major 4, minor 0)
# crw-rw-rw- 1 root root  1,  3 Jul 1 ... /dev/null  (char, major 1, minor 3)
```

**Major number:** identifies the driver (8 = SCSI/SATA disk driver)
**Minor number:** identifies the specific device (0 = whole disk, 1 = partition 1)

**Special devices:**
```bash
/dev/null       — discard writes, return EOF on reads
/dev/zero       — return infinite zeros on reads
/dev/urandom    — non-blocking CSPRNG (cryptographic random bytes)
/dev/random     — blocking CSPRNG (waits for entropy; modern Linux: same as urandom)
/dev/full       — always returns ENOSPC on writes (testing)
/dev/mem        — access physical RAM (requires root, restricted in modern kernels)
/dev/kmem       — access kernel virtual memory
/dev/stdin      — symlink to /proc/self/fd/0
/dev/stdout     — symlink to /proc/self/fd/1
/dev/stderr     — symlink to /proc/self/fd/2
```

**Creating device files:**
```bash
# mknod creates device files:
mknod /dev/myvirtdev c 200 0   # character device, major 200, minor 0
# The kernel driver with major 200 handles I/O on this file
```

## 9. Network File Systems via VFS

VFS enables mounting remote files as if they were local:

**NFS (Network File System):**
```bash
# Mount remote server's /exports/data at local /mnt/nfs:
mount -t nfs 192.168.1.100:/exports/data /mnt/nfs

# NFS client implements VFS operations by sending RPC calls to the server:
read() → NFS_READ RPC → server reads from ext4 → returns data
write() → NFS_WRITE RPC → server writes to ext4

# Files appear local to applications — transparent!
ls /mnt/nfs/  # works just like local ls
```

**SMB/CIFS (Windows shares):**
```bash
# Mount Windows share:
mount -t cifs //192.168.1.101/SharedFolder /mnt/windows \
    -o username=alice,password=secret

# Now /mnt/windows looks like a local ext4 directory to Linux programs
```

**tmpfs:**
```bash
# In-memory file system — no disk at all:
mount -t tmpfs -o size=256m tmpfs /dev/shm

# Files in /dev/shm are in RAM — extremely fast IPC for shared memory
# /dev/shm is the standard location for POSIX shared memory (shm_open)
# Cleared on every reboot
```

## 10. How VFS Dispatches a System Call

**Full trace: `fd = open("/etc/passwd", O_RDONLY)`**

```
1. syscall: openat(AT_FDCWD, "/etc/passwd", O_RDONLY)

2. VFS path resolution:
   - Start at root dentry (cached in current namespace)
   - Lookup "etc" in root dentry → find dentry for /etc (check dcache first)
   - Lookup "passwd" in /etc dentry → find dentry for /etc/passwd

3. Get inode:
   - /etc/passwd dentry → points to inode 123456 on ext4

4. Permission check:
   - inode has mode 0644, uid=0, gid=0
   - Calling process: uid=1000, gid=1000
   - O_RDONLY: check read bit for "others" → r is set → allowed

5. Allocate struct file:
   - Create new open file table entry
   - f_op = inode->i_fop (pointing to ext4_file_operations)
   - f_pos = 0

6. Call file system open:
   - ext4_file_open() called if present
   - Sets up file-specific state

7. Allocate file descriptor:
   - Find lowest available fd in process's fd table
   - fd[3] = pointer to struct file
   - Return 3 to user space

Later: read(3, buf, 1024)
   → kernel looks up fd[3] → struct file
   → calls file->f_op->read_iter(file, &kiocb, &iov_iter)
   → dispatches to ext4_file_read_iter()
   → ext4 finds the data blocks, reads from disk (or page cache)
   → copies data to user space buffer
   → returns number of bytes read
```

## Summary

| Concept | Description |
|---------|------------|
| VFS | Kernel abstraction layer providing uniform interface for all file systems |
| super_block | Represents a mounted file system; holds FS-wide operations |
| inode | Represents a file/directory; holds metadata + operations table |
| dentry | Directory entry: name → inode mapping; cached in dcache |
| file | Per-open-file state: current offset, flags, operations table |
| Mount point | Location in directory tree where a new file system is grafted |
| Mount namespace | Per-process view of the file system tree (used by containers) |
| /proc | Pseudo-FS exposing process and kernel state as readable files |
| /sys (sysfs) | Pseudo-FS exposing device model and kernel parameters |
| /dev | Device files; major:minor numbers identify device drivers |
| NFS | Network File System; VFS makes remote files look local |
| tmpfs | In-memory file system; no disk backing; cleared on reboot |
| dcache | Dentry cache; avoids repeated path lookups for same names |
| Dispatch | VFS calls appropriate function pointer (ext4_read, nfs_read, proc_read) |
