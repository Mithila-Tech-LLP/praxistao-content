## 1. The Attack Surface

**The OS attack surface:**
```
External attack vectors:
  Network: malformed packets, protocol exploits
  Files: malicious document opens → exploit document parser
  Devices: malicious USB device (BadUSB), Thunderbolt DMA attack

Local privilege escalation:
  Application exploits → get shell as www-data
  Kernel exploit → elevate www-data to root
  Hypervisor escape → escape from VM to host

Insider attacks:
  Malicious user with login access
  Supply chain: malicious library or build tool
```

**Exploit goals (typical privilege escalation chain):**
```
Remote code execution (RCE) on a service:
  → Arbitrary code as the service's user (e.g., www-data)
  → Privilege escalation via kernel exploit or misconfig
  → Root/SYSTEM access
  → Persistence (write cron job, systemd service, rootkit)
```

## 2. Buffer Overflow Attacks

**The classic attack — C has no bounds checking:**

```c
// Vulnerable function:
void handle_request(char *input) {
    char buffer[128];
    strcpy(buffer, input);  // strcpy doesn't check length!
    // If input is > 128 bytes, it writes past the end of buffer
}
```

**Stack layout before overflow:**
```
High addresses (bottom of diagram)
┌────────────────────────────────┐
│   Previous stack frame         │
│   ...                          │
│   Saved RBP (frame pointer)    │ ← buffer[127+8..+15]
│   Return address (RIP)         │ ← buffer[127+16..+23] ← OVERWRITE THIS!
│   Function arguments           │
├────────────────────────────────┤
│   buffer[127]                  │
│   buffer[126]                  │
│   ...                          │
│   buffer[0]                    │ ← &buffer[0] = RSP
└────────────────────────────────┘
Low addresses (top of diagram)
```

**Attack:**
```
Send input: [128 bytes garbage][8 bytes for RBP][address of shellcode]

strcpy copies all of this into buffer (which only has space for 128 bytes)
The extra bytes overwrite saved RBP and then RETURN ADDRESS
When handle_request() returns:
  CPU pops the return address → now points to attacker's shellcode
  CPU jumps to shellcode → executes attacker's code!
```

**Classic shellcode:**
```nasm
; x86-64 shellcode that executes /bin/sh:
xor rdi, rdi
push rdi               ; null terminator for string
mov rdi, 0x68732f2f6e69622f  ; "/bin//sh" in little-endian
push rdi
mov rdi, rsp           ; rdi = pointer to "/bin//sh"
xor rsi, rsi           ; argv = NULL
xor rdx, rdx           ; envp = NULL
mov rax, 59            ; execve syscall
syscall                ; call execve("/bin//sh", NULL, NULL)
```

**Defenses:**

1. **Safer functions:** Use `strncpy(buf, input, sizeof(buf))`, `snprintf()`, `strlcpy()` — these check length.
2. **Stack canaries**
3. **ASLR**
4. **NX/W^X bit**
5. **Address Sanitizer (for testing)**

## 3. Stack Canaries

**Stack canary** — a random value placed between local variables and the return address:

```
Stack with canary:
┌────────────────────────────────┐
│   Previous stack frame         │
│   Saved RBP                    │
│   Return address               │
├────────────────────────────────┤
│   CANARY VALUE  (random!)      │ ← placed here by function prologue
├────────────────────────────────┤
│   buffer[127]                  │
│   ...                          │
│   buffer[0]                    │
└────────────────────────────────┘
```

**Function prologue (generated by compiler with -fstack-protector):**
```c
// Conceptually, the compiler inserts:
void handle_request(char *input) {
    long canary = __stack_chk_guard;  // read random value from thread-local storage
    char buffer[128];
    
    strcpy(buffer, input);  // potentially overflows
    
    // Before returning, check if canary is intact:
    if (canary != __stack_chk_guard) {
        __stack_chk_fail();  // logs and kills the process
    }
}
```

**Why it helps:**
To overwrite the return address, the attacker must also overwrite the canary. But the canary is random (set at program start via /dev/urandom), and the attacker doesn't know its value.

If the canary is corrupted when the function returns → the process is killed before the attack succeeds.

**Bypasses:**
- **Format string attack:** Read canary from stack before overflowing
- **Information leak:** Some other bug reveals the canary value
- **Heap overflow:** Doesn't go through the stack → canary irrelevant
- **Overwrite canary with same value:** If you know the canary value

**Enabling:**
```bash
gcc -fstack-protector-strong myprogram.c   # protect functions with arrays/alloca
gcc -fstack-protector-all myprogram.c      # protect ALL functions
```

## 4. Return-Oriented Programming (ROP)

**The problem for attackers after NX bit:**
ASLR + NX together mean:
- Shellcode can't be injected into data (NX)
- Even if shellcode was somewhere, you don't know its address (ASLR)

**ROP (Return-Oriented Programming):** Instead of injecting shellcode, chain together EXISTING executable code (in kernel, libc, the binary itself) to perform arbitrary operations.

**Gadgets:** Short sequences of instructions ending in a `ret` (or `jmp rsp`, etc.):
```
; Gadget 1: found in libc at some address:
pop rdi; ret        ; load first argument

; Gadget 2: found in libc:
pop rsi; ret        ; load second argument

; Gadget 3: system() call address (in libc)
; system(cmd) = executes a shell command

; Gadget 4: address of "/bin/sh" string (inside libc)
```

**ROP chain:**
```
Overwrite return address with gadget 1's address
Then: [address of "/bin/sh"]     ← popped into rdi by gadget 1
Then: [address of gadget 2]      ← where gadget 1 rets to
Then: [0]                        ← popped into rsi by gadget 2
Then: [address of system()]      ← where gadget 2 rets to
```

When the function returns → executes: pop rdi → pop rsi → call system("/bin/sh")
Without injecting any new code!

**Defenses against ROP:**
- **CET (Control-flow Enforcement Technology):** Intel hardware support for shadow stacks + indirect branch tracking. Shadow stack: a separate stack storing only return addresses, not modifiable via normal memory writes. On `ret`, CPU checks return address against shadow stack.
- **CFI (Control Flow Integrity):** Compiler instruments indirect calls to only allow calls to valid targets.
- **ASLR:** If you don't know where libc is loaded, you don't know gadget addresses.
  (ROP requires knowing exact addresses → ASLR makes this harder, info leaks defeat it)
- **Stack canaries:** Don't stop ROP but complicate buffer overflows

## 5. Heap Exploitation

Heap exploits corrupt the allocator's metadata to achieve arbitrary writes.

**Use-after-free:**
```c
char *buf = malloc(256);
free(buf);
// ... later...
buf[0] = 'A';  // writing to freed memory!
// If another object was allocated at the same address, we're corrupting it
```

**Double-free:**
```c
free(ptr);
free(ptr);  // freeing already-freed memory!
// In glibc's tcache, this can link the chunk into the free list twice
// Next two mallocs return the SAME pointer → two pointers to the same buffer
// Writer via ptr1 corrupts ptr2's data
```

**Heap overflow:**
```c
char *buf = malloc(100);
memcpy(buf, attacker_data, 500);  // overflow!
// Overwrites next chunk's header → can corrupt another object
// Or manipulate the size field → return an overlapping chunk on next malloc
```

**Modern heap mitigations in glibc:**
- Chunk size validation on free
- Tcache key to detect double-free (stores a key in freed chunk's `fd` pointer)
- Safe linking: encode free list pointers with ASLR randomness
- `MALLOC_CHECK_` environment variable for debugging

## 6. Kernel Exploits

Kernel vulnerabilities are the most dangerous because once exploited, the attacker has full root (or can disable all security measures).

**Types of kernel vulnerabilities:**

**Kernel null pointer dereference:**
```c
// Vulnerable kernel code:
void process_packet(struct sk_buff *skb) {
    struct iphdr *ip = ip_hdr(skb);
    if (ip->protocol == IPPROTO_TCP) {
        struct tcphdr *tcp = tcp_hdr(skb);  // might return NULL!
        tcp->dest = 80;  // ← NULL pointer dereference → kernel crash (panic)
    }
}
// Attacker: craft a packet that makes tcp_hdr() return NULL
// → if exploitable: write to address 0 + offset → controlled write!
```

**Kernel use-after-free:**
```c
// Race condition in kernel:
void cleanup(struct device *dev) {
    free_irq(dev->irq, dev);   // free the IRQ handler
    kfree(dev);                 // free the device struct
    // ... later, interrupt fires after kfree but before irq is fully released ...
    // dev pointer is dangling → use-after-free
}
```

**Privilege escalation via kernel exploit:**
```c
// After gaining arbitrary write in kernel:
// 1. Find the task_struct for the current process
// 2. Overwrite cred->uid to 0 (become root)
// Or:
// 1. Find the page table entries for malicious pages
// 2. Make them executable → execute arbitrary kernel code
```

**Famous kernel exploits:**
- Dirty COW (CVE-2016-5195): Race condition in copy-on-write mechanism — local user → root
- Dirty Pipe (CVE-2022-0847): Overwrite read-only files via page cache — local user → root
- Spectre/Meltdown: Side-channel attacks leaking kernel memory

**Kernel hardening:**
```bash
# Enable kernel self-protection features:
# CONFIG_RANDOMIZE_BASE — KASLR (kernel ASLR, randomize kernel base address)
# CONFIG_STACKPROTECTOR — stack canaries in kernel code
# CONFIG_FORTIFY_SOURCE — detect overflows in kernel string/memory functions
# CONFIG_HARDENED_USERCOPY — validate copy_to/from_user bounds
# CONFIG_SLAB_FREELIST_RANDOM — randomize slab allocator freelist
# CONFIG_INIT_ON_FREE_DEFAULT_ON — zero memory on free (prevent use-after-free leaks)

# Check at runtime:
cat /proc/sys/kernel/kptr_restrict   # 2 = hide kernel pointers from /proc
cat /proc/sys/kernel/perf_event_paranoid  # restrict perf usage
cat /proc/sys/kernel/dmesg_restrict  # restrict dmesg access
```

## 7. Side-Channel Attacks — Meltdown and Spectre

**The fundamental problem:** Modern CPUs perform **speculative execution** — they execute instructions ahead of time, before knowing if they're needed. If speculated instructions access secret data, traces can be read via timing.

**Meltdown (CVE-2017-5754):**
```
1. CPU speculatively executes:
   rax = *kernel_address    ; read kernel memory (normally would be blocked by page fault)
   ; Page fault happens (delayed)
   ; BUT: speculatively, this data is in rax

2. Attacker code:
   rbx = user_array[rax * 4096]  ; access user array at offset derived from secret
   ; If rax = 0x42, CPU loads cache line for user_array[0x42 * 4096]

3. Page fault arrives, CPU discards rax, unwinds speculative execution
   (looks like nothing happened... but cache is not undone!)

4. Attacker measures timing:
   for (i = 0; i < 256; i++) {
       time_t = time(access(user_array[i * 4096]));
       if (time_t < threshold) {
           // This cache line is warm → rax was i → secret byte = i!
           leaked_byte = i;
       }
   }
```

**Meltdown fix: KPTI (Kernel Page Table Isolation)**
Separate page tables for user/kernel mode. When running user code, kernel pages are NOT in the page table at all → no speculative access possible.
```bash
cat /sys/devices/system/cpu/vulnerabilities/meltdown
# Mitigation: PTI  (or "Not affected" on newer CPUs)
```

**Spectre (CVE-2017-5753):**
More subtle — exploits the branch predictor:
```
// Victim code in kernel:
if (index < array_size) {        // bounds check
    return array2[array1[index] * 4096];  // read
}

// Attacker "trains" the branch predictor:
// Make many calls with valid index → predictor learns "this branch is usually taken"

// Attacker calls with index = secret_kernel_address - array1:
// Branch predictor: "I bet the bounds check passes" → speculatively executes the read
// Read leaks data from kernel via cache timing
```

**Spectre mitigations:**
- IBRS/IBPB/STIBP: CPU microcode to restrict branch predictor speculation
- Retpoline: Compiler technique to prevent JIT speculation across security boundaries
- LFENCE: Serialize instruction stream (prevent speculative read past fence)

```bash
cat /sys/devices/system/cpu/vulnerabilities/spectre_v1
cat /sys/devices/system/cpu/vulnerabilities/spectre_v2
# Shows current mitigation status
```

## 8. Defense Layers Summary

Modern OS security relies on multiple layers, each defending against different attacks:

```
Layer 1: Input validation (application level)
  → Prevent buffer overflows, SQL injection, format strings
  → Use safe APIs: strncpy, snprintf, bounded reads

Layer 2: Compiler defenses (compile time)
  → Stack canaries (-fstack-protector-strong)
  → AddressSanitizer for testing
  → CFI (Control Flow Integrity)
  → SafeStack (separate stack for return addresses)

Layer 3: OS memory protection
  → NX/W^X: data pages not executable
  → ASLR: randomize base addresses
  → RELRO: make GOT read-only after init (prevents function pointer overwrite)

Layer 4: Privilege separation
  → Drop root after startup (run as www-data, not root)
  → Linux capabilities instead of full root
  → seccomp filters (limit available syscalls)
  → chroot/namespaces (restrict file system view)

Layer 5: MAC / mandatory policy
  → SELinux/AppArmor: even if compromised, limits what attacker can do
  → Allow only required syscalls, file accesses, network connections

Layer 6: Kernel hardening
  → KASLR: randomize kernel base address
  → SMEP: prevent kernel from executing user pages
  → SMAP: prevent kernel from accessing user memory
  → KPTI: separate page tables (Meltdown mitigation)
  → Kernel stack canaries, HARDENED_USERCOPY

Layer 7: Monitoring and response
  → Audit logs (auditd, SELinux AVC denials)
  → IDS/IPS
  → eBPF-based monitoring
```

## Summary

| Attack | Mechanism | Defense |
|--------|-----------|---------|
| Stack buffer overflow | Write past buffer to overwrite return address | Bounds-checking APIs, stack canaries, ASLR, NX |
| Heap exploitation | Corrupt allocator metadata or use-after-free | Safe allocator, memory tagging, ASAN |
| ROP | Chain existing code gadgets to bypass NX | ASLR, CFI, shadow stack (CET) |
| Kernel null deref | Access address 0 in kernel | Map null page prevention, SMAP |
| Use-after-free | Access freed memory | Memory tagging (MTE), init-on-free |
| Race condition | TOCTOU in kernel | Locking, atomic operations |
| Meltdown | Speculative access to kernel memory via cache timing | KPTI (separate page tables) |
| Spectre | Train branch predictor to speculatively access secret data | Retpoline, microcode updates |
| Format string | %n writes to attacker-controlled address | Use safe printf wrappers; no user-controlled format strings |
| ASLR bypass | Information leak reveals base addresses | Eliminate info leaks; PIE binaries |
