## 1. What Is a Page Fault?

A **page fault** is a hardware exception generated by the MMU when a virtual address translation fails.

The MMU raises a page fault when:
1. The page is **not present** (present bit = 0 in the PTE)
2. The access **violates permissions** (write to read-only, user accessing kernel page)
3. The virtual address is **not mapped** at all (no PTE exists)

**What happens hardware-side:**
```
CPU tries to access virtual address V
  ↓
MMU looks up page table entry
  ↓
PTE.present == 0 (or address not mapped, or permission violation)
  ↓
CPU generates Page Fault exception (#PF, interrupt vector 14 on x86)
CPU pushes error code and fault address onto stack
CPU jumps to OS page fault handler (registered in IDT)
```

**Fault address:**
On x86, the faulting virtual address is stored in the CR2 register when a page fault occurs. The error code indicates: was it a read or write? In user or kernel mode? Was the PTE present?

## 2. Types of Page Faults

**Minor page fault (soft fault):**
The page needs to be mapped, but the data is already in memory somewhere (page cache, zero-fill buffer, COW shared page).
- Cost: ~1–10 μs
- No disk I/O needed
- Common during program startup (shared library pages mapped from page cache)

**Major page fault (hard fault):**
The page must be read from disk (swap file, or mapped file not yet in memory).
- Cost: ~1–10 ms (SSD) or ~5–100 ms (HDD)
- Disk I/O required
- Process blocks until disk read completes

**Invalid access (segmentation fault):**
Access to unmapped address or permission violation:
- OS checks VMA (virtual memory area) for the address
- Not in any VMA → invalid access → OS sends SIGSEGV to the process
- In a VMA but wrong permissions (write to read-only) → same result: SIGSEGV

**Stack growth fault:**
Access slightly below the current stack end → OS expands the stack (if within limit):
- Process accesses 0x7fffffffe000 but stack only goes to 0x7ffffffff000
- OS checks: is this "near" the current stack? → yes → add a page to the stack
- Common during function calls that use lots of local variables

## 3. The Page Fault Handler — Step by Step

When the OS receives a page fault:

```
Page fault handler (simplified):

1. Read faulting address from CR2
2. Read error code: read/write? user/kernel? present bit?

3. Find the VMA containing the faulting address
   - Search process's VMA list for VMA such that vma.start ≤ addr < vma.end
   - If not found: SIGSEGV (invalid address)

4. Check permissions
   - Is the access type (read/write/execute) allowed by the VMA?
   - If not: SIGSEGV (permission violation, e.g., write to read-only mapping)

5. Handle the fault based on VMA type:

   CASE A: Anonymous mapping (heap, stack, zero-initialized memory)
     - Allocate a new physical page
     - Zero-fill it (security: don't leak data from previous process)
     - Map it in the page table with appropriate permissions
     - Return → resume faulting instruction

   CASE B: File-backed mapping (executable, shared library, mmap'd file)
     - Find the page in the page cache (in-memory cache of file data)
     - If found in page cache: map it → return (minor fault)
     - If not in page cache: allocate a physical page, read from disk, map it (major fault)
     - Return → resume faulting instruction

   CASE C: Swap-backed page (previously evicted to swap)
     - Allocate a new physical page
     - Read the page from the swap space on disk
     - Map it in the page table
     - Return → resume faulting instruction

   CASE D: COW (copy-on-write, write to shared page)
     - Allocate a new physical page
     - Copy the existing shared page's contents to the new page
     - Update the PTE to point to the new page (read-write)
     - Decrement reference count on the old shared page
     - Return → resume faulting instruction

6. Invalidate TLB entry for the faulting address
   (The new PTE must be seen by the CPU for the resumed instruction)

7. Return from exception → CPU resumes the faulting instruction
   (Now the address is mapped → this time the access succeeds)
```

## 4. Demand Paging — Load Pages Only When Needed

**Demand paging** means: don't load anything into RAM until the program actually accesses it.

**When a program starts (exec):**
Without demand paging: load the entire binary into RAM, then start.
With demand paging: set up page table entries pointing to the file, but mark everything NOT PRESENT. Start executing immediately. Load pages as they're accessed.

**Result:**
- Program starts in milliseconds (nothing to load upfront)
- Only the pages that are actually used consume RAM
- A program with 100MB binary that only uses 2MB of code → only 2MB of RAM used

**What exec() does with demand paging:**
```c
// exec() doesn't copy the binary into RAM!
// Instead:
// 1. Create new address space (new page tables)
// 2. Create VMA for each segment: text, data, bss
// 3. Set up text VMA: vm_file = binary_file, all PTEs NOT PRESENT
// 4. Set up data VMA: vm_file = binary_file, all PTEs NOT PRESENT
// 5. Set up BSS VMA: anonymous (zero-fill), all PTEs NOT PRESENT
// 6. Set up stack: one page initially
// 7. Jump to entry point

// When CPU fetches first instruction:
//   → page fault (code page not present)
//   → OS reads first code page from binary file into RAM
//   → maps it, returns to instruction
//   → CPU fetches instruction, executes it
//   → program is running!
```

**Measurable benefit:**
On a Linux system, run: `time ls`. The `ls` binary is maybe 200KB. With demand paging, the kernel only loads the pages actually executed (most of the time, a few KB). Without demand paging, it would load all 200KB.

## 5. Page Fault Performance

Page faults have different costs depending on what needs to happen:

| Type | Typical Cost | What happens |
|------|-------------|-------------|
| Minor fault (already in page cache) | 1–5 μs | Just update page table |
| Zero-fill anonymous page | 3–10 μs | Allocate page, zero it, update PT |
| Major fault (NVMe SSD) | ~100 μs | Disk I/O + update PT |
| Major fault (HDD) | 5–15 ms | Slow disk I/O + update PT |
| Swap read (NVMe) | ~200 μs | Read from swap + update PT |
| Swap read (HDD) | 10–30 ms | Very slow |

**Program startup is dominated by page faults:**
A typical application like Firefox might take 2–5 seconds to start. Much of that is page fault time for loading code and data.

**How to see page faults:**
```bash
/usr/bin/time -v ls /tmp

# Output includes:
# Major (requiring I/O) page faults: 0
# Minor (reclaiming a frame) page faults: 327
```

```bash
# For a running process:
cat /proc/1234/stat | awk '{print "minor faults:", $10, "major faults:", $12}'
```

## 6. Swap Space — More Virtual RAM Than Physical

When physical RAM is full, the OS can **evict** (move) pages to disk (swap space). This frees RAM for other uses.

**Swap eviction:**
```
RAM is 90% full.
OS chooses a "victim" page (using a page replacement algorithm — Chapter 21).
If page is dirty (modified): write it to swap → mark PTE not present + set swap info
If page is clean (unchanged copy of a file): just discard → mark PTE not present
The physical frame is now free for reuse.

Later, when the process accesses the swapped-out address:
  → page fault
  → OS reads page from swap back into RAM
  → updates PTE with new physical address
  → resumes the process
```

**Swap space configuration:**
```bash
# Check swap usage:
free -h
# Output:
#               total        used        free
# Swap:         8.0Gi        1.2Gi       6.8Gi

# Create additional swap:
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
```

**Swap performance:**
- NVMe SSD swap: 200 μs per page → acceptable
- SATA SSD swap: 500 μs per page → tolerable
- HDD swap: 10–30 ms per page → painful

**Swappiness:**
Linux has a `vm.swappiness` sysctl parameter (0–100) that controls how aggressively the OS swaps:
- 0: Only swap when absolutely necessary (prefer reclaiming file cache)
- 100: Swap aggressively (desktop workloads may prefer this)
- Default: 60

```bash
cat /proc/sys/vm/swappiness  # view current value
sudo sysctl vm.swappiness=10  # set to 10 (desktop use)
```

## 7. Copy-on-Write (COW) Page Faults

`fork()` creates a child process that is an exact copy of the parent. Naively, this requires copying all the parent's memory — gigabytes potentially. That would be slow.

**COW optimization:**
After `fork()`:
1. Parent and child share the same physical pages
2. Both page tables point to the same physical frames
3. All shared pages are marked READ-ONLY in both page tables
4. Neither parent nor child can write to them yet

When either process tries to WRITE to a shared page:
```
Write to shared page
  → page fault (write to read-only page)
  → OS detects: this is a COW fault (VMA has VM_WRITE but page is read-only)
  → Allocate a new physical page
  → Copy the shared page's contents to the new page
  → Map the new page in the WRITING process's page table (read-write)
  → Decrement refcount on the original page
  → Resume the write instruction on the new page
```

**Result:**
- `fork()` is fast (nanoseconds to copy page table entries, no data copying)
- Only pages that are actually written get copied
- Pages never written (code, libraries, read-only data) are NEVER copied — shared forever

**COW and shared pages:**
Shared libraries (libc, libpthread, etc.) use COW. One physical copy shared by thousands of processes. Only the tiny amount of writable data in those libraries gets copied per process.

**COW and security:**
A subtle attack: "dirty COW" (CVE-2016-5195). An attacker could race between writing to a COW page and the OS detecting the write to escalate privileges. Fixed by proper memory ordering in the Linux kernel.

## 8. Memory-Mapped Files and Page Faults

When a file is `mmap()`'d into memory, pages are loaded on demand via page faults:

```c
int fd = open("bigfile.dat", O_RDONLY);
void *data = mmap(NULL, file_size, PROT_READ, MAP_SHARED, fd, 0);
// No file data is read yet!

// Access element 1000:
int value = ((int*)data)[1000];
// → page fault: the page containing offset 4000 is not in RAM
// → OS reads that page from the file (or finds it in page cache)
// → resumes access
// → returns the value
```

**Page cache:**
The kernel maintains a page cache (also called buffer cache) — pages from files that have been read into RAM. If multiple processes mmap the same file, they all share the same physical pages from the page cache.

```
File: /lib/libc.so.6
  ↓  mmap'd by process A (PID 1234) at virtual 0x7f00000
  ↓  mmap'd by process B (PID 5678) at virtual 0x7f00000
  ↓  mmap'd by process C (PID 9012) at virtual 0x7f00000

Physical RAM page 0x100000 contains libc's first page
  - PID 1234's page table maps virtual 0x7f00000 → physical 0x100000 (read-only)
  - PID 5678's page table maps virtual 0x7f00000 → physical 0x100000 (read-only)
  - PID 9012's page table maps virtual 0x7f00000 → physical 0x100000 (read-only)

ONE physical copy, THREE mappings. Memory efficient!
```

## 9. Working Set and Thrashing

**Working set:**
The set of pages a process actively needs at any given moment.

If physical RAM can hold the working sets of all running processes → fast operation.
If physical RAM is smaller than the sum of all working sets → thrashing.

**Thrashing:**
```
RAM is full.
Process A needs page X → evict page Y (belongs to process B)
Process B needs page Y → evict page Z (belongs to process C)
Process C needs page Z → evict page X (belongs to process A!)
Process A needs page X again → evict page Y again...
∞ loop of swapping
```

**Symptoms of thrashing:**
- CPU is nearly idle (processes are all waiting for disk I/O)
- Disk activity is 100%
- System completely unresponsive to user
- `vmstat 1` shows very high `si`/`so` (swap-in/swap-out) columns

**Detecting thrashing:**
```bash
vmstat 1
# procs  memory        swap   io
#  r  b  swpd  free    si  so  bi  bo
#  2  8  5000  1000  1000 1000  800 1000
#        ↑     ↑      ↑   ↑
#     lots of swap   heavy swap activity → thrashing!
```

**Solutions to thrashing:**
1. Add more RAM (most effective)
2. Reduce the number of running processes (kill some)
3. Use swap on fast storage (NVMe instead of HDD)
4. Use huge pages (larger pages = fewer TLB misses, more work done between faults)
5. Use `vm.swappiness=0` (swap less aggressively, let processes die if OOM instead)

## 10. Prefetching — Predicting Future Faults

The OS can try to prefetch pages before they're needed:

**Sequential prefetch:**
If a process is reading pages 0, 1, 2 sequentially, the OS prefetches pages 3, 4, 5 in advance.

Linux does this automatically with its "readahead" mechanism:
```bash
cat /sys/block/sda/queue/read_ahead_kb  # current readahead size
sudo blockdev --setra 256 /dev/sda       # set 128KB readahead
```

**madvise() — hint to OS:**
Programs can tell the OS their access pattern:
```c
#include <sys/mman.h>

// Tell OS: I'm going to access this range sequentially
madvise(ptr, length, MADV_SEQUENTIAL);  // OS increases readahead

// Tell OS: I'm going to access this range randomly
madvise(ptr, length, MADV_RANDOM);  // OS disables readahead (useless)

// Tell OS: I need this page soon — prefetch it now
madvise(ptr, length, MADV_WILLNEED);  // OS starts async I/O

// Tell OS: I'm done with this range — free the pages
madvise(ptr, length, MADV_DONTNEED);  // OS can reclaim these pages
```

Used by databases, virtual machines, and performance-sensitive applications to tune page fault behavior.

## 11. Handling Out-of-Memory (OOM)

When the system has no more RAM and no swap, or swap is exhausted, it's an OOM (Out-of-Memory) situation.

**OOM killer:**
Linux has an "OOM killer" that selects a process to kill when memory is completely exhausted.

Selection criteria (OOM score):
- Memory usage (larger processes are preferred victims)
- CPU time (short-running processes preferred)
- Nice value (low-priority processes preferred)
- oom_score_adj (per-process tuning)

```bash
# View OOM score for a process:
cat /proc/1234/oom_score

# Adjust OOM score (-1000 = never kill, 1000 = kill first):
echo -500 > /proc/1234/oom_score_adj  # protect this process from OOM killer
echo 900 > /proc/1234/oom_score_adj   # prefer to kill this process on OOM
```

**Dmesg output when OOM killer fires:**
```
[1234567.890123] Out of memory: Kill process 9876 (chrome) score 950 or sacrifice child
[1234567.890456] Killed process 9876 (chrome) total-vm:2097152kB, anon-rss:1048576kB
```

**Prevention:**
- Don't overcommit: `vm.overcommit_memory = 2` disables overcommit (fail `malloc()` if no physical memory available)
- Cgroups: limit memory per container/group of processes (Kubernetes uses this)
- OOM avoidance at application level: check `malloc()` return values; handle NULL

## Summary

| Concept | Definition |
|---------|-----------|
| Page fault | Hardware exception when MMU can't translate virtual address |
| Minor fault | Page in memory but not mapped; no disk I/O needed |
| Major fault | Page must be read from disk; expensive |
| Invalid access (SIGSEGV) | Accessing unmapped address or violating permissions |
| Demand paging | Load pages only when first accessed; fast startup |
| Swap space | Disk area for evicted pages; slower than RAM |
| Eviction | Moving a page from RAM to swap to free a frame |
| COW | Copy-on-write after fork(); share until write, then copy |
| Page cache | In-memory cache of file pages; shared between processes |
| Working set | Pages a process actively uses; fits in RAM = no thrashing |
| Thrashing | Constant paging in/out because working sets exceed RAM |
| OOM killer | Linux mechanism to kill processes when RAM is exhausted |
| madvise() | Application hint to OS about future memory access patterns |
